# Decisions

Recorded before implementation; updated as evidence changes. Alternatives are explicit so a later redesign can revisit a choice.

1. **Hub layout.** Choose a group rail, global search, and a responsive visual card grid, with incremental card loading and a compact heading once there are saved references. Alternatives: a flat bookmark list (dense but poor visual recall), rigid kanban columns per group (large groups overwhelm narrow screens), or keeping the large welcome hero after save (hides cards below the fold). Keep original group names, colours and order; never auto-cluster.
2. **Fragment marking.** Choose text selection through a page context-menu command and visible-region drag through a lightweight injected overlay. Alternatives: always-on content scripts (more access and page interference), full-page screenshot (expensive and often impossible), and manual cropping in a separate editor (too slow). An unsaved page can be saved as a single card when a fragment is marked; an existing saved URL is enriched rather than duplicated.
3. **Storage.** Choose per-group/card metadata in `chrome.storage.local`, image blobs and fragment records in extension IndexedDB, plus `unlimitedStorage`. Alternatives: sync (violates one-machine privacy/size requirements), images as storage data URLs (quota pressure), and one giant metadata array (read-modify-write loss and scale). Browser profile removal can still remove data; local storage is not backup.
4. **Save ordering.** Capture all URLs and metadata, write and read back every card and its group, then close only unchanged, successfully saved tabs. A failure leaves tabs open with an explicit error. Alternative: close once a storage call is started; rejected because losing even one reference is unacceptable. Preview and AI failures never block metadata capture.
5. **Visuals.** Prefer the newest cropped, user-marked region/passage; then an active-tab viewport screenshot if captured; otherwise a locally cached page-owned OG/Twitter image; finally a styled site/title panel. Chrome cannot screenshot an inactive tab; never switch the user's active tab just for capture. Failed/unavailable images must not display as broken tags. No remote assets are loaded in the hub.
6. **AI guess.** Use one `GuessProvider` interface with a no-op provider and an implementation using Chrome's built-in on-device `LanguageModel` in the extension page. Do not use hosted inference or silently download a model. If unavailable, show no model guess; notes and fragments still work. The guess is editable, and user edits take priority.
7. **Build tool.** WXT with React, TypeScript, Tailwind and shadcn/ui components. WXT's discovered popup/hub/background entrypoints and extension hot reload fit this MV3 project with less bespoke configuration than CRXJS. Bundle all code locally; no CDN.
8. **Permissions.** Request tab, group, context-menu, scripting and broad site access for one-action group metadata/preview extraction across arbitrary pages. The broad permission is a deliberate privacy/UX tradeoff: data is retained only locally and network image requests are made solely to cache a page's own preview. Restricted browser pages still save their tab metadata.
9. **Theme bootstrap.** Keep the shared light/dark token set in one local stylesheet and run a locally bundled theme module before React. MV3's extension CSP prohibits an inline theme script; a bundled first script preserves the behavior without relaxing CSP.
10. **Preview network boundary.** The hub fetches only a page-declared HTTP(S) preview after a save, without cookies or referrer, accepts limited image MIME types up to 2.5 MB, caches the bytes in IndexedDB and displays only a blob URL. Alternatives: linking directly to remote images (repeated tracking requests) or relying on background screenshots for inactive tabs (unsupported).
11. **Repeated and unsaved fragments.** Append every marked passage/region to an IndexedDB list per card rather than overwriting a previous mark; keep each cropped image under its own fragment ID. Attach a new mark to the most recently saved exact URL, then to its hash-free URL if necessary. If no card exists, create a single-tab card but leave the live tab open. Alternatives: overwrite old marks (data loss), update every duplicate card (changes unrelated group context), or close the tab as a side effect of marking (surprising).
12. **Independent editable metadata.** Save notes and model/user interpretations under their own `chrome.storage.local` keys instead of rewriting a whole card. This prevents a model guess from racing with a note edit. An interpretation corrected by the user is never replaced by an automatic guess; dirty dialog edits require a save or an explicit discard.
13. **User-controlled backup.** Provide complete local `.tabhub` ZIP exports and non-destructive imports containing group/card metadata, independent notes/guesses, fragment lists and image bytes. Reject conflicts instead of overwriting local records. Alternatives: metadata-only JSON (would discard the visuals) or automatic cloud backup (violates the privacy scope). The in-memory archive has an explicit 500 MB restore limit; streaming archives are a later scalability improvement.
14. **Bounded enrichment and scale.** Show cards in batches of 48; permit four concurrent preview downloads per hub page, a five-second image timeout, a 2.5 MB image limit and a two-second page metadata timeout. Alternatives: eagerly load hundreds of images or delay the save until every site responds. A 600-card browser run met the interactive threshold without adopting heavier virtualization.
15. **Hub reuse and active navigations.** Reuse an open hub tab rather than creating another on each save. Prefer a tab's pending destination over its old URL and leave it open if navigation changes before close. Restricted browser pages still keep their link metadata and an intentional text fallback; an unsaveable group is never closed.
16. **Formatted guide copy.** Declare `clipboardWrite` and write both semantic `text/html` and a `text/plain` alternative only after the user clicks **Copy formatted text**. Do not request clipboard-read access. Alternatives: plain text only (loses heading/list structure) or copying rendered CSS/classes (produces brittle pasted content).
17. **Curated planning handoff.** Keep a generated `claude-handoff/` folder with canonical product documents, a compact research synthesis and selected synthetic screenshots—never source code or private browsing data. Make stale handoff contents fail the standard test command. Alternatives: connect Claude to the full repository (unnecessary context/token cost) or maintain an ad hoc manual handoff (quickly drifts).
18. **Archive, not timed deletion.** Make archive a reversible view state for one card, a selected set, or a complete saved browser group. Store separate per-card/per-group sidecars in `chrome.storage.local` so URLs, notes, fragments and images are never removed or overwritten. A group archive hides every card; restoring the group leaves individually archived cards hidden. Restoring one card inside an archived group makes an explicit exception for that archive epoch; re-archiving the group hides it again. Alternatives: automatic expiry after 90 days (violates "nothing is ever lost"), destructive delete or rewriting whole card records (data-loss/race risk).
19. **Search and backups after archive.** Main search excludes archived cards; the Archived view searches only archived cards. Preserve archive states in complete `.tabhub` exports while importing pre-archive backups with every card active. Old backups need no migration; a conflicting archive state is refused just like a conflicting note. Extend the curated planning handoff with one synthetic archive screenshot.
